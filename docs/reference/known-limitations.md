# Known Limitations

This document describes known limitations of the `unusedfunc` analyzer and provides workarounds for each case.

## Template Method Calls

**Status**: Known limitation

### Description

Methods called exclusively from Go template files (`.tmpl`, `.gotmpl`, `.html`) can be reported as unused. The analyzer does not parse template files or resolve template text to method calls.

### Example

```go
// batch.go
type TemplateContext struct {
    data string
}

// This method is called from template but can be reported as unused.
func (t *TemplateContext) Export() string {
    return t.data
}

// template.gotmpl
{{ .Export }}
```

### Workaround

Use suppression comments to mark template methods as intentionally used:

```go
//nolint:unusedfunc // used in template.gotmpl:15
func (t *TemplateContext) Export() string {
    return t.data
}
```

Or use the `lint:ignore` pattern:

```go
//lint:ignore unusedfunc used in batch-esm-runner.gotmpl
func (t *TemplateContext) Export() string {
    return t.data
}
```

## Generated Files

**Status**: Limited flag behavior

`--skip-generated` defaults to true, but it does not exclude generated functions from candidate collection, SSA construction, suppression loading, or reporting. It filters only the AST declaration map used for runtime-directive detection. It recognizes comments containing `Code generated`, `DO NOT EDIT`, `autogenerated`, or `AUTO-GENERATED`.

Do not use this flag as a workaround for generated-code findings. Suppress a known dynamic use or exclude that code from the package pattern instead.

## Assembly Function Calls

**Status**: Partially handled

### Description

Functions called exclusively from assembly (`.s`) files may be reported as unused when they are not recognized.

### Example

```go
// function.go
func asmImplemented() int // Implemented in assembly

// impl.s
TEXT ·asmImplemented(SB), $0-8
    MOVQ $42, ret+0(FP)
    RET
```

### Current Handling

The analyzer includes assembly file scanning:
- Detects package-local direct `TEXT ·FunctionName(SB)` declarations
- Detects package-local direct `CALL ·FunctionName(SB)` invocations
- Does not report assembly-implemented functions and roots direct assembly calls

### Limitations

- Cannot track cross-package assembly calls
- Does not handle indirect assembly references
- Only the `TEXT` and `CALL` forms above are recognized

### Workaround

For edge cases not detected, use suppression comments:

```go
//nolint:unusedfunc // called from assembly: impl_amd64.s:42
func lowLevelFunction() { ... }
```

## `//go:linkname` Directives

**Status**: Partially handled

### Description

Functions aliased via `//go:linkname` directives may not have their aliasing relationships fully tracked.

### Example

```go
//go:linkname internalFunc runtime.externalFunc
func internalFunc() { ... }
```

### Current Handling

The analyzer examines only a function declaration's `Fn.Doc` comment group. A recognized declaration-attached `//go:linkname` directive marks that function as used to avoid false positives.

### Limitations

It does not inspect arbitrary file comments, model the alias relationship, or use calls through an alias to prove reachability of another declaration.

### Workaround

Functions with a supported `//go:linkname` directive are automatically marked as used. If a dynamic linkname-related use is still reported, use a suppression comment.

## Reflection Patterns

**Status**: Conservative handling

### Description

Methods called via reflection may be reported as unused unless they match known reflection patterns.

### Known Safe Patterns

At SSA root selection, exact names `String`, `GoString`, `Error`, `Marshal`, `Unmarshal`, `Validate`, `Decode`, and `Encode` are applied only to package-level members. They do not root methods with those names.

Separately, RTA scans a currently visited function for mapped static calls to JSON, fmt, XML, YAML, gob, binary, or `database/sql` APIs. An empty-interface conversion in such a function selectively retains exported methods whose names are in the union of that call's mapped methods and the unconditional fallback: `MarshalJSON`, `UnmarshalJSON`, `MarshalText`, `UnmarshalText`, `String`, `GoString`, `Error`, and `Format`. This mapping includes JSON v2 entry points and streaming hooks. It is a function-wide heuristic, not general argument-level reflection or string-flow analysis.

Direct SSA uses of interface conversions as `reflect.ValueOf` or `reflect.TypeOf` arguments retain exported methods even alongside mapped calls. This exception does not trace through stores, control-flow joins, or wrapper functions. Methods with their own type parameters are not retained solely for reflection.

### Limitations

Custom reflection patterns, `reflect.Value.MethodByName` names, method names stored in registries or maps, struct tags, and custom callback-registration APIs may not be detected.

### Workaround

```go
//nolint:unusedfunc // called via reflect.Value.MethodByName in customHandler
func (t *Type) CustomReflectionMethod() { ... }
```

## Uninstantiated Generic APIs

**Status**: Conservative partial handling

Normal mode retains public generic functions and methods without a local instantiation. Because these templates cannot be ordinary RTA roots, a typed-AST fallback follows function/method references and direct concrete-to-interface boundaries, then analyzes concrete helpers with RTA.

The fallback does not model general value flow through containers, fields, multi-result expressions, or generic call chains. Helpers used only through such paths can still be reported. A concrete instantiation exercised by tests enables ordinary SSA analysis; otherwise suppress a confirmed use with a reason.

## Configuration-Dependent Code

**Status**: Expected behavior

### Description

Functions that are used only under specific build tags or configurations may appear unused when analyzing with different settings.

### Example

```go
//go:build linux

package platform

func linuxSpecificFunction() { ... } // Used only on Linux builds
```

### Why This Happens

The analyzer sees only the code visible under the current build configuration. Functions conditional on different build tags can be reported in a configuration where their uses are absent.

### Workaround

Run the analyzer once for each configuration of interest:

```bash
# Analyze Linux build
GOOS=linux unusedfunc ./...

# Analyze Windows build
GOOS=windows unusedfunc ./...
```

Or use suppression comments for platform-specific code:

```go
//nolint:unusedfunc // used on Linux builds
func linuxSpecificFunction() { ... }
```

---

## Test Code

**Status**: Always included

Package loading always includes test variants. Test, benchmark, and example functions are roots, so uses from loaded test code participate in reachability. There is no CLI flag to disable or enable test-file loading.

---

## Suppression Comment Reference

The analyzer supports multiple suppression comment formats on a function declaration or its preceding line.

### Format 1: `nolint` Style
```go
//nolint:unusedfunc
func myFunction() { ... }

//nolint:unusedfunc // reason for suppression
func myFunction() { ... }
```

### Format 2: `lint:ignore` Style
```go
//lint:ignore unusedfunc reason for suppression
func myFunction() { ... }
```

### Best Practices

1. Always include a reason explaining why the function is used
2. Reference the location of use (file:line) when applicable
3. Keep suppression comments close to the function declaration
4. File-wide suppressions are not supported

## Getting Help

If you encounter a false positive not covered by these known limitations:

1. Check if it matches a documented limitation above
2. Try suppression comments as a workaround
3. File an issue with a minimal reproducible example
4. Include the function signature, usage location, command, build tags, and analyzer output

For questions about whether behavior is a bug or expected limitation, consult this document first.
